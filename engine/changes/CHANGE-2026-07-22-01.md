## Goal
修复 `engine-verify.{sh,ps1}` 的 checkpoint.md append-without-dedup bug。当前实现每次 AC verify PASS 都向 `engine/evidence/T-NNN/checkpoint.md` 末尾追加一行,不检查该 AC-N 是否已有 PASS 条目。后果:T-036 checkpoint.md 111 行(18 ACs × 6 轮 verify),T-034 60 行,T-035 51 行——均超出契约 ≤4KB ~100 行预算,SessionStart 注入时逼近 N1=400 行上限。

根因:契约源 FILE 15 明确写了"追加写,不覆盖历史行",这是设计错误(不是实现 bug)——verify 是唯一写入者,同 AC-N 重复 PASS 无信息价值,只有时间戳更新有意义。

## Impact Scope
checkpoint.md 是 SessionStart 优先注入的 AC 级恢复锚点。dedup 修复直接影响所有未来 verify 行为:同 AC 重复 verify PASS 不再追加新行,只更新时间戳。影响范围:契约源(1 份) + dist(1 份) + verify 脚本(4 份 sh/ps1) + skeleton(2 份) + 现有 checkpoint.md(5 份) + 测试(2 份新建) + 版本文件(3 份) + CHANGELOG + manifest + 本 change 卡。

## Risk & Watchpoints
- **dedup 算法只对 `^- \[x\] AC-N ` 行生效**:header 与其他行不动。如果未来 verify 写入其他格式的 AC 行(如 `- [ ]` 未完成),dedup 不会处理——目前 verify 只写 `- [x]` PASS 行,无风险
- **header 时间戳不刷新**:首次 PASS 创建 checkpoint.md 时写 "Last updated: <ts>",后续 PASS 不刷新 header 时间戳(只更新 AC 行的时间戳)。这是设计选择——header 标记文件创建时间,AC 行标记最新 verify 时间。测试 Test 2 已验证此行为
- **bash grep -v 在空文件上返回非零退出码**:用 `2>/dev/null || true` + `[ -s tmp ]` 检查避免误删;PowerShell Where-Object 在空数组上返回空,Set-Content 写空文件后 Add-Content 追加——两者均安全
- **plugin manifest SHA 更新**:.ps1 和 VERSION 的 SHA256 已更新;.sh 的 SHA 在 AC-2 完成时已同步过(无需重复更新)
