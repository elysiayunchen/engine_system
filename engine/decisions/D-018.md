# D-018 — Phase 1 通用化核心的实施设计

> status: proposed | scope: contract/**, engine/bin/**, engine/prompts/**, engine/scripts/**, plugin/**, install.sh, install.ps1, engine/tasks/**, engine/decisions/**, engine/changes/**, engine/CONTEXT.md, engine/HANDOFF.md | expiry: never | supersedes: none | related: D-017

## 背景

Phase 0 管道加固 3/3 完成(T-016/017/018,verify 全绿)。D-017 实施路线的下一步是
Phase 1「通用化核心(prompt 抽离 / CLI 扩展 / 快速安装 / agent 检测)」。

设计勘察发现两个关键实况,直接塑造本决策:

1. **init prompt 已经单源化**。`plugin/.claude/commands/engine-init.md`(2456 行)是
   `contract/src/`(cli-preamble + [0-9]*.md)的编译产物(D-015),与 web 版
   `ENGINE_FILE_SYSTEM_v5.md` 同源。所谓「prompt 抽离」不是从零抽,而是**给同一真相源
   增加一个 agent 中立的分发形态**——目前唯一分发副本躺在 `.claude/commands/` 这个
   Claude Code 专属位置,其他 agent 在用户项目里没有约定俗成的取用点。
2. **`plugin/bin/*` 与 `engine/bin/*` 没有任何同步机制**(compile 不覆盖 bin,
   check.sh 也无 bin 漂移门),当前一致纯属人工纪律。本决策首次系统性改 bin,
   隐患变现实风险,须顺手治理。

另:运营文件曾把 Phase 1 复述为「去 Claude-Code 专属依赖、多 agent 适配层」,与
D-017 原文四子项口径略有漂移;本决策以 D-017 原文为准,回写时一并校正。

## 决策

### D-018a · init prompt 增加 agent 中立分发形态(修正 D-017a「薄壳」措辞)
- compile 新增第 5 个 dist:`contract/src/agent-preamble.md`(新增,agent 中立前言)
  + 同一批 `[0-9]*.md` 契约模块 → **`engine/prompts/init.md`**(仓库正本),
  并镜像同步到 `plugin/engine/prompts/init.md`(与 engine/scripts 分发模式同构)
- 经 manifest + install.{sh,ps1} 分发,用户项目在 `engine/prompts/init.md` 获得
  任何 agent 都能读的 init prompt
- slash 版 `engine-init.md` **保留全量编译产物,不改薄壳**
- **Why**: Codex/Copilot/Cursor/web 用户从此在项目内有约定取用点;「prompt 不分叉」
  由编译同源保证,三个 prompt dist 共用一套契约模块
- **对 D-017a 的修正(需架构师认可)**: D-017a 写「.claude/commands/engine-init.md
  变成薄壳引用」。编译同源已把薄壳的维护收益归零,而薄壳会引入运行时间接层
  (agent 读 2456 行超长文件的截断风险、目标文件缺失的边界),纯增风险零收益。
  故「不分叉」目标改由编译层达成,分发层保持全量
- **Alt rejected**: slash 薄壳化(如上);维持现状(其他 agent 拿不到 prompt);
  运行时拼接(无编译保障,漂移回归)

### D-018b · `engine init` 子命令:终端侧 agent 无关入口
- `engine/bin/engine` + `engine.ps1` 新增 `init`:定位 `engine/prompts/init.md` →
  缺失则指引 `engine update` 修复 → `engine/ENGINE_MAP.md` 已存在则提示已初始化
  (指向 /engine-reconcile),但仍继续输出指引 → 默认打印人类可读指引
  (prompt 路径 + 各 agent 用法示例),`--print` 纯输出 prompt 正文供管道/复制
- `engine init` **只打印、零写入**——真正生成引擎文件的是拿到 prompt 的 agent
- **Why**: 补齐 D-017a 的 CLI 半边;print-first 对任何 agent 通用,无 TTY 交互复杂度
- **Alt rejected**: 自动拉起 agent CLI(交互接管越权、跨 agent TTY 兼容成本高,
  Phase 2+ 再议);CLI 内做采访向导(重复 agent 的活,违背「引擎是文件层」)

### D-018c · agent 检测 = 共享检测器脚本(T-020)
- 新增 `engine/scripts/engine-detect-agents.{sh,ps1}` 孪生:检测 PATH 上的 agent
  CLI(claude/codex/copilot/cursor…)与项目内目录痕迹(.claude/ 等),
  输出一行一个 agent 标识
- `engine init` 与 install.{sh,ps1} 收尾指引消费检测结果,只显示命中 agent 的用法,
  未命中给通用指引
- **Why**: 检测逻辑集中一处,避免 install.sh/ps1 + bin 孪生四处内联漂移;
  这是 D-017c「原生最优」在 Phase 1 的最小落地(指引个性化)
- **Alt rejected**: 各消费点内联检测(四份漂移);Phase 1 就做完整 adapter 指南
  (那是 Phase 3 / D-017d Step 2 的活)

### D-018d · 快速安装骨架 = 静态模板走既有分发机制(T-021)
- `plugin/engine/skeleton/{ENGINE_MAP,CONTEXT,HANDOFF}.md` 三个自描述空模板,
  manifest/FILES 各增 3 条,dest 为 `engine/*.md`、`protect=false`
- 分发语义由既有机制自动成立:fresh 装且缺失才铺,update 永不覆盖用户记忆
  (installer 现有 protect + skip 规则,零新逻辑分支);离线包/校验/清单门自动覆盖
- 骨架 ENGINE_MAP 自述「空模板,跑 `engine init`(终端)或 `/engine-init`(agent)
  填充」→ 装完 2 分钟内看到结构与下一步(D-017b)
- **Alt rejected**: 安装器 heredoc 生成(sh/ps1 双份模板漂移);init 时才生成
  (安装完看不到任何结构,违背 2 分钟见价值)

### D-018e · bin 副本纳入 compile 同步(定向治理)
- compile.{sh,ps1} 增加 bin 同步步:`engine/bin/{engine,engine.ps1,engine.cmd}` →
  `plugin/bin/`(engine/bin 为唯一真相源,与 scripts 同构)
- **Why**: 本决策工作路径首次触碰 bin;无同步机制的隐患在此变成现实风险
