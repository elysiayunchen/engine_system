## Context — 真实案例与怀疑历程

### 案例

`study_engine`(诺识/Noēsis)项目已升级到 v6.2.0,VERSION=6.2.0、管理层契约齐备,但 v6 数据层完全空转:0 任务卡 / 0 决策 / 0 AC JSON,80 份 v5 changes 成孤儿数据。

### 已否决的方案(记录怀疑历程,供未来 architect 参考)

**Option C(promote-v5 helper + 4 个 Doctor check + 契约 §3.6)** — 否决理由:
- 把 v5 数据强行转成 v6 原语有语义错位(把"已显见的"转成"待决策的 proposed",把"已验证的"转成"unverified stub")
- AC JSON 的 verify 字段是命令输出+sha256 指纹,无法从 v5 evidence.md 反推 → stub 是伪造结构
- promote-v5 后 Doctor 立刻 PASS(因为 tasks>0),空转上移一层——D-021 想消除的"空转通过"在更高层重演
- T-025 AC-13 的 verify 命令是恒真式(`|| echo`),自证失效

**Option D(v5 归档为只读 prior-art + Doctor 持续报差距)** — 否决理由:
- 与 contract/src/30-operational.md SYNC step 5 的 "additive migration" 语义互斥
- prior-art 引用指向 v6 工具拒绝维护的解析器,指针语义不闭合
- 只是一次性方案,不解决"后续版本继续迭代"问题

**三层可持续演进方案(schema_version + 多跳迁移链 + 考古层化)** — 否决理由:
- schema_version 是第四个无人消费的死字段(engine/VERSION + 根 VERSION + contract-version 已有三个,且 contract-version grep 确认零消费代码)
- run_migrate() 调度器已存在于 engine/bin/engine(第 82-125 行),v6.1/v6.2 step 从未创建——机制空转根因是"没人写 step",不是"缺少框架"
- managed block 全量替换(upsert_block)与 step 增量链架构互斥
- idempotent "文件不存在才创建"无法为已存在文件补字段——schema_version 永远不会被加到老项目的 rules.json
- 考古层化与 git history 重复(git 已是考古层)
- 过度工程:9+ 文件、200+ 行代码、击穿 budget,而核心问题只需 5-10 行 Doctor check

### 已发现的真实 bug(优先修复)

**VERSION 卡死循环**:`run_migrate` 跑 v6.0.sh 成功 → 回写 `engine/VERSION=6.0.0`。因无 v6.1/v6.2 step,VERSION 停在 6.0.0。回退跑 migrator,但 `ensure_structure` 只在 `! -f` 时创建 engine/VERSION,不更新已存在文件。结果:engine/VERSION=6.0.0、根 VERSION=6.2.0、Doctor 永久 warn "differs - run engine migrate to sync",用户照做 → 无新 step → 回退 migrator → 不改 VERSION → **修复路径自身卡死**。

## Root Cause(修正后)

不是"缺少桥接框架",而是两个具体问题:
1. **VERSION 卡死 bug**:migrator 不更新已存在的 engine/VERSION
2. **Doctor 缺格式特征检测**:只检查"存在性"(tasks/T-*.md 是否存在),不检查"格式充分性"(changes/ 有数据但 tasks/ 空、rules.json 仍是默认值等)

## Decision — MVP 方案

### 1. 修复 VERSION 卡死 bug(必修)

`engine-migrate-contract.sh` 的 `ensure_structure()` 在最后强制同步 `engine/VERSION` 到当前工具版本(不是 "if not exists"):

```bash
# 当前(有 bug):
if [ ! -f "$ENGINE_DIR/VERSION" ]; then
  ...create...
fi

# 修复后:
# 始终同步到当前工具版本(已是 idempotent——值相同则无副作用)
printf '%s\n' "$CONTRACT_VERSION" > "$ENGINE_DIR/VERSION"
```

.ps1 双实现同步。

### 2. Doctor 加"格式特征检测"check(核心)

新增 `check_legacy_data_format()`(版本无关,检测格式特征而非版本号):

- 任务卡无 v6 头(无 `write-set:` / `status:` 字段)→ WARN "可能是老格式任务卡"
- rules.json protected_paths 仍是 migrator 默认单元素 `["runtime-law.md"]` → WARN "protected_paths 未配置,参考 v6 完整版"
- changes/ 有 capsule 但 tasks/ 空 → WARN "changes 有 N 份 capsule 但 0 张任务卡——新工作请用 v6 任务卡"
- evidence/ 有 .md 但无 T-NNN/AC-N.json → WARN "evidence 是老格式 .md,新工作请用 evidence/T-NNN/AC-N.json"

**关键设计**:check 检测"格式特征"而非"版本号"。任何版本的老格式都会被检测。未来 v6→v7 时,只要 v7 改了格式,Doctor check 就会检测到(可能需要更新 check 的特征,但不需要新机制)。

### 3. migrator 结尾条件化提示(对新用户零冗余)

migrator 结尾检测是否有老格式残留:
- 有残留 → 提示 "Detected N legacy data files. New work should use v6 task cards/decisions/AC JSON."
- 无残留 → 输出 "Migration complete. No further action needed."

新用户 init 后无残留 → 看到简洁提示。老项目有残留 → 看到具体数字 + 指引。

### 4. 不引入新概念

- 不引入 schema_version(用 engine/VERSION)
- 不引入 migration chain(用现有 run_migrate + reconcile_schema)
- 不引入考古层化(用 git history)
- 不引入新目录
- 不引入新契约规则(Doctor check 是脚本行为,不是契约规则)
- 不动 contract/budget.json
- 不动 plugin/manifest.json
- 不动 install.sh

## Consequences — 诚实回答"能一劳永逸吗?"

**不能。** 任何方案都不能一劳永逸。但本方案设计为"可持续":

### 为什么不能一劳永逸

- 未来 v7 可能引入全新的数据层(比如替代任务卡的"工作流卡")——届时需要新的 check
- 未来 v7 可能删除某个数据层(比如 decisions/ 被废弃)——届时需要迁移策略
- 这些场景无法用"通用框架"预覆盖,因为未来的格式变化不可预测

### 为什么本方案可持续

- **检测逻辑是"格式特征"而非"版本号"**——任何老格式都会被检测,不依赖版本号比对
- **每次迭代的成本是"改 5 行代码"**——未来 v7 发版时,开发者只需:
  1. 更新 Doctor check 的格式特征(5 行代码)
  2. 可选:在 reconcile_schema 加 inline 修复
  3. 可选:写一个新 migration step(如果迁移复杂)
- **不引入新概念/新字段/新目录**——未来维护者不需要理解"schema_version 与 engine/VERSION 的关系"等额外抽象
- **复用现有机制**——run_migrate 调度器已存在,reconcile_schema inline 修复已存在,Doctor run_custom_checks 扩展点已存在
- **git history 承担考古层**——不重复造轮子
