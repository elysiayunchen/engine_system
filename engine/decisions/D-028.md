## Decision

1. **批准 LPHP(Large Project Handover Pack)作为 v6.7.0 ~ v6.10.0 的方向主题**,分 4 个 minor 版本落地,每个版本独立验证、失败可回退。不作为单一 v6.7.0 主题一次全上——4 项改造任一都是 minor 版本量级,合并发布风险过大。

2. **版本路线与痛点对应:**
   | 版本 | 任务卡 | 痛点 | 核心机制 |
   |------|--------|------|---------|
   | v6.7.0 | T-032 | 压缩后丢失细节 | 任务级 progress.md(7 栏)+ SessionStart hook 机器强制注入 |
   | v6.8.0 | T-033 | 遗漏已有代码 | 域级 INVENTORY.md(≤120 行总览 + 子文件)+ 双向 FAIL 检查 + ast-grep 委托 |
   | v6.9.0 | T-034 | 任务没跑完就压缩 | AC 级 checkpoint.md + 任务粒度软门禁(超阈值须拆卡或声明 checkpoint_plan)+ depends-on 显式依赖 |
   | v6.10.0 | T-035 | 跑出死代码 | verify 调用原生 linter(shellcheck + PSScriptAnalyzer)+ 反向调用点扫描 + WARN 升级为 done 门 |

3. **强制力来源全部为机器强制**(不依赖 agent 自觉):
   - T-032:progress.md 接入 SessionStart hook,active 卡存在时机器自动注入
   - T-033:INVENTORY 双向 FAIL 检查,code↔INVENTORY 任一方向失配 = doctor exit 非 0
   - T-034:违反软门禁的任务卡不能置 active(FAIL);depends-on 上游未 done 阻塞下游
   - T-035:warn_count > 0 时 done 须架构师显式豁免,未豁免 = FAIL

4. **明确不做的(对照原 TRAIL 提案与子代理审视):**
   - 不引入 PreCompact hook——已证实机制错配(hook 不让 agent 写盘,只给注入文本机会)
   - 不自研 AST 解析器——违反 CLI-LEAN,符号定位交 ast-grep / ctags 现生
   - 不引入**运行时**上下文预算感知——依赖 IDE/agent 特定 hook(如 Claude Code context 计数 hook),Engine System 不能跨适配器承诺。**静态预执行预算估算**可行,见 §10 机制 A
   - 不硬失败所有 WARN——只让 warn_count > 0 时 done 须豁免(T-035)
   - 不覆盖**语义级**软死代码(换名重写、换实现重做)——靠 T-033 INVENTORY 人审兜底。**字面复制子集 + API 名重复子集**可机器检查,见 §10 机制 B/C
   - 不替代 HANDOFF.md 会话级恢复——T-032 progress.md 在 active 卡存在时让 HANDOFF 立即恢复点退化为薄指针,但不替代其会话级职能

5. **修订记录(对原 LPHP 提案的 4 处改造,基于子代理审视):**
   | # | 原提案 | 修订后 | 理由 |
   |---|--------|--------|------|
   | 1 | P1 任务粒度 WARN | 降级为辅助;主线改为 AC 级 checkpoint 机制 | WARN 在 Engine System 里是失效设计,Doctor WARN 不入 exit code;AC checkpoint 直接降损害 |
   | 2 | P2 progress.md 4 栏 + "压缩后 MUST Read" | 扩为 7 栏;接入 SessionStart hook 机器强制注入;事件驱动更新 | 漏了 SessionStart 这条最关键路径,靠 agent 自觉等于没机制 |
   | 3 | P3 INVENTORY 单文件 | 分级:≤120 行总览 + 子文件;双向 FAIL 检查;明确边界(INVENTORY 只写语义,符号定位交 ast-grep) | 缺强制注入通道 + 缺反向漂移检查 + 与 derivable 工具边界模糊 |
   | 4 | P4 自研跨语言扫描器 | 委托原生 linter(shellcheck + PSScriptAnalyzer 优先);WARN 升级为 done 门项 | 自研扫描器在 shell+ps1+md 仓不可行;WARN 无 done 门挂载等于没机制 |

6. **修订后能解决的痛点边界(诚实声明):**
   | 用户痛点 | 基础机制覆盖率 | 补 §10 机制 A/B/C 后覆盖率 |
   |---|---|---|
   | 任务没跑完就压缩 | **部分**——AC checkpoint 降损害,不消除压缩本身 | **部分+**——机制 A(静态预算软门禁)在执行前挡住「明显过大」任务卡,覆盖率 +30% |
   | 压缩后丢失细节 | **是**——progress.md 接入 SessionStart hook 是机器强制,7 栏覆盖完整 | **是**(无变化) |
   | 遗漏已有代码 | **是**——INVENTORY + ast-grep 组合,语义层人写 + 符号层机器现生 | **是**(无变化) |
   | 跑出死代码 | **部分**——linter 抓硬死代码,软死代码(冗余复刻)仍需 INVENTORY 兜底 | **部分+**——机制 B(jscpd 字面复制检测)+ 机制 C(INVENTORY API 唯一性)覆盖率 +30% |

   **总覆盖率从 2.5/4 提升至约 3.3/4**,剩余 0.7 是真固有边界:任务运行时压缩本身 + 语义级软死代码(换名重写、换实现重做)。这是短上下文 agent 接管大项目的固有边界,不是设计缺陷。

7. **依赖关系(6 份审视后修订):**
   - T-033 **硬依赖** T-032(progress.md §3「已排除路径」与 INVENTORY 互补)
   - T-035 **硬依赖** T-033(软死代码兜底靠 INVENTORY)
   - T-034 **弱依赖** T-032(工程上独立,可与 T-032/T-033 并行开发;但 T-034 spec.md 的 SessionStart 重锚优先级链 #2 progress.md / #4 HANDOFF 薄指针为 T-032 落地后激活的兼容层,T-032 未落地时退化为 #1 checkpoint.md → #3 任务卡头直连)
   - 4 张任务卡的 `decision: D-028` 字段已在前序步骤写入,本决策批准后即可开干 T-032
   - **依赖图**:`T-032 ──→ T-033 ──→ T-035`,`T-034 ──(weak forward-ref)──→ T-032`

8. **版本策略 + expiry 执行约束(6 份审视后补充):**
   - 每个版本独立 release,走标准 `scripts/release.sh` 流程
   - 每个版本独立验证(plugin 镜像 + manifest + check.sh + 三处 VERSION + CHANGELOG)
   - 失败可回退——任一版本验证不通过,回退到上一 tag,不影响后续版本规划
   - 不跨版本累积改动——每个版本的 WRITE-SET 严格限定本版本范围
   - **T-034 (v6.9.0) 必须与 T-033 (v6.8.0) 并行开发**,pilot 串行发版;若 T-034 开发晚于 T-033 发版启动,触发早期预警——3 个月窗口需靠此并行节省 10 天
   - **pilot 不阻塞下一版本**——pilot 在版本 release 后并行进行,问题以 patch 版本修复,与 D-026/D-027 先例一致
   - **早期预警**:2026-09-15(过期前 45 天)若 v6.7.0 未发版,触发架构师审视——此时 3 个月窗口已消耗 58 天,临界路径已无可能 3 个月内完成 4 版本,应立即调整 scope 或拆分
   - **到期未完成处置**:优先拆分(D-028 → superseded + 新开 D-028a approved 已落地部分 + D-029 proposed 未完成部分);次选续期一次至 2027-01-31,禁止二次续期

## 9. 迁移宽限期原则(6 份审视后新增,必须改补丁)

所有新增 FAIL 检查对 contract-version 低于该机制引入版本的老项目降级为 WARN,与 `check_legacy_data_format()` 范式对齐。

| 机制 | 引入版本 | 老项目(contract-version < 引入版本)判定 | 新项目(contract-version ≥ 引入版本)判定 |
|---|---|---|---|
| T-032 `check_progress_md` | 6.7.0 | active/paused 卡无 progress.md = WARN | active/paused 卡无 progress.md = FAIL |
| T-033 INVENTORY→code 方向 | 6.8.0 | INVENTORY 行指向的 Entry file 不存在 = WARN | = FAIL |
| T-033 code→INVENTORY 方向 | 6.8.0 | 已 done 任务涉及文件未在 INVENTORY 出现 = WARN | = FAIL |
| T-033 migrator 写 INVENTORY stub | 6.8.0 | migrator 在升级时写入空表头 stub 到 `engine/domains/<domain>/INVENTORY.md` | — |
| T-034 软门禁 FAIL | 6.9.0 | 违反阈值 = WARN(仅提示) | = FAIL |
| T-034 depends-on FAIL | 6.9.0 | 上游未 done 阻塞下游置 active = WARN | = FAIL |
| T-035 warn_count > 0 done 门 | 6.10.0 | done 时 warn_count > 0 须豁免 = WARN | = FAIL |

**实现路径**:每个新增 `check_*` 函数读 `ENGINE_DOCTOR.md` 首行 `<!-- contract-version: X -->` 标记,小于引入版本时调 `warn` 而非 `fail`。Migrator 已通过 `upsert_block` 自动写入 contract-version 头,无需额外改动。

**T-034 bypass**:除迁移宽限外,显式允许 `checkpoint_plan: tryout` 作为合法 bypass 值——架构师开试错卡时可声明 `checkpoint_plan: tryout`,软门禁 FAIL 降级为 WARN。`check_task_granularity` 只检查字段非空,不检查内容。

**T-035 批量豁免**:DEAD-CODE.json 顶层加 `"exempt_all": true, "exempt_reason": "<理由>"` 字段。`check_warn_done_gate` 优先读顶层,`exempt_all: true` 视为全部 entry 已豁免,不需逐条标。保留 per-entry `exempt` 作为细粒度选项。

## 10. 机制扩展 A/B/C(6 份审视后新增,应该改补丁)

针对原 LPHP 提案 3 处「过早放弃」,补 3 项机器可检查的机制,把覆盖率从 2.5/4 提升至约 3.3/4。

### 机制 A:WRITE-SET 静态预算软门禁(挂 T-034 AC-5.1)

- **针对痛点**:任务没跑完就压缩
- **机制**:在 T-034 现有三阈值(AC>12 / 独立路径>15 / estimated_steps>20)之外,新增第 4 阈值——**WRITE-SET 列出的所有文件总字节数 > 30KB(≈ 8000 tokens)** 时触发软门禁,须拆卡或显式声明 `checkpoint_plan` 才能置 active
- **强制力级别**:FAIL(与 T-034 现有软门禁同级;迁移宽限期同 §9)
- **预期覆盖率提升**:剩余「任务粒度本身」痛点的 30~50%
- **实施成本**:低。Doctor 脚本对 WRITE-SET 列出的路径求 `wc -c` 之和,无 AST、无运行时 hook、无新依赖。脚本增量 < 30 行(双份 sh+ps1 镜像)
- **与「不引入运行时上下文预算感知」的兼容性**:严格兼容。运行时预算感知需 hook 进运行时 context 计数(已声明不做);静态预算估算是执行前对磁盘文件求和,机制完全不同

### 机制 B:jscpd 委托(挂 T-035 AC-2.1)

- **针对痛点**:软死代码中的**字面复制子集**(约占软死代码 30~40%)
- **机制**:verify 调用 jscpd 扫描 WRITE-SET 触及的 .sh / .ps1 / .md 文件,token 阈值与最小块长用 jscpd 默认;输出 `evidence/T-NNN/COPY-PASTE.json`;命中即计 `warn_count`,走 T-035 现有「warn_count > 0 须架构师显式豁免」done 门
- **强制力级别**:WARN(计入 T-035 已有的 warn_count→done 门,不新增门级)
- **预期覆盖率提升**:软死代码痛点的 30~40%(仅限字面复制子集)
- **实施成本**:低。jscpd 是 npm 包,verify 脚本调用方式与 shellcheck 一致(fallback 策略一致:不可用降级到 skip + WARN)。脚本增量约 40 行(双份)
- **与「不自研 AST 解析器」的兼容性**:完全兼容。jscpd 是第三方现成工具,prismjs tokenizer 不是 Engine System 自研,符合 CLI-LEAN「符号定位交现生」精神
- **边界**:对「换名重写」「换实现重做」的语义重复无效——那部分确实只能靠 INVENTORY 人审,属固有边界

### 机制 C:INVENTORY API 唯一性机器检查(挂 T-033 AC-6.1)

- **针对痛点**:软死代码中的**显式 API 重复子集**(约占软死代码 20~30%)
- **机制**:T-033 AC-1 已规定 INVENTORY 模板含「Public API」列。本机制要求 Doctor 扫描所有域的 INVENTORY.md + 子文件,「Public API」列出现的 API 名**全仓唯一**,重复 = FAIL。可选进阶:对 Feature 列做归一化(去空格、小写)后查重,捕获「同功能不同名」的明显情况
- **强制力级别**:FAIL(与 T-033 现有双向 FAIL 检查同级;迁移宽限期同 §9)
- **预期覆盖率提升**:软死代码痛点的 20~30%
- **实施成本**:极低。Doctor 脚本 grep INVENTORY.md 的 API 列 + sort + uniq -d,不到 20 行(双份)
- **与「不覆盖语义级软死代码」的兼容性**:对原声明的**精确化**而非推翻。原声明隐含「INVENTORY 兜底 = 人审」,本机制把其中的「API 名重复」子集升级为机器检查,人审范围收窄到「同功能不同名」的语义判断

### 机制 A/B/C 落地策略

3 项机制作为 AC 增项挂载到现有任务卡(T-033 AC-6.1 / T-034 AC-5.1 / T-035 AC-2.1),**不新开任务卡、不新开版本号**。各任务卡执行时落实,若执行中发现某机制不合适可单独移除该 AC,不影响其他机制与版本发布。

## Consequences

- **常驻上下文增量可控:** T-032 progress.md 只在 active 卡存在时注入(不进 SessionStart 全文),T-033 INVENTORY 只首行摘要进域仪表盘——与 D-027 常驻压缩精神一致。
- **强制力升级:** 4 项机制全部 FAIL 级或 done 门,不依赖 agent 自觉;WARN 在本路线里只作辅助预警或迁移宽限期降级,不作主要强制力。
- **复杂度上升:** 新增 2 个文件类型(progress.md / INVENTORY.md)+ 1 个 evidence 子类型(checkpoint.md / DEAD-CODE.json / COPY-PASTE.json)+ 4 处 Doctor 检查 + 2 处 hook 改造(SessionStart / verify)+ 3 项机制扩展(§10 A/B/C)。系统学习成本上升,但每项都有 machine checkpoint 兜底。
- **与 D-027 的张力:** T-032 progress.md 本质是再引入一个会持续增长的任务级文件。靠 7 栏单行强制 + done 归档机制(progress.md 在任务 done 时归档到 `engine/archive/tasks/T-NNN-progress.md`,不进 SessionStart)对称控制,与 D-027 HANDOFF 归档同款策略。
- **迁移宽限期对称:** §9 表确保老项目升级时不被新 FAIL 检查立即阻塞;contract-version 标记是机器可读的,与 `check_legacy_data_format()` 同款范式。
- **范围诚实:** 修订后(含 §10 机制 A/B/C)能解决 4 个痛点中的约 3.3 个,不解决任务运行时压缩本身与语义级软死代码——这是短上下文 agent 接管大项目的固有边界。本决策不承诺根治,只承诺把可机制化的部分机制化。

## Options Considered

- **A. LPHP 分阶段落地(本决策选定)**——4 个 minor 版本,每版独立验证,失败可回退。
- B. LPHP 单一 v6.7.0 主题一次全上——风险过大,任一项失败会阻塞整版。
- C. 只做 TRAIL(原提案)——已证实只解决 1/4 个问题的 1/N 部分,边际收益极低。
- D. 不做 LPHP,把精力放到真实大库试点——可行但延后了机制化;真实大库试点反而需要 LPHP 的 INVENTORY 才能高效进行,先做 LPHP 更合理。
- E. 引入 PreCompact hook 抢救压缩前内容——已证实机制错配,hook 不让 agent 写盘,只给注入文本机会;放弃。

## Rationale

用户提出的 4 个痛点(任务没跑完就压缩 / 压缩后丢失细节 / 遗漏已有代码 / 跑出死代码)是短上下文 agent 接管大型项目的结构性问题,不是单个窄缝(如 TRAIL)能解决。6 份子代理审视证实原 LPHP 提案方向正确但实现路径有 4 处硬伤(WARN 失效 / 漏 SessionStart / 自研 AST / WARN 无 done 门)+ 3 处过早放弃(运行时预算与静态预算混为一谈 / 字面复制未走第三方 CPD / API 唯一性未机器化)。修订后(含 §9 迁移宽限期 + §10 机制 A/B/C)能解决约 3.3 个痛点——剩下的 0.7 个是真固有边界。

分阶段而非一次全上,是因为 4 项改造任一都是 minor 版本量级,合并发布风险过大且失败难以定位。每个版本独立验证、失败可回退,是 D-026 发布门精神在路线层面的延伸。
