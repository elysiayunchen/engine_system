# D-029: 多 Claude Code 实例并行抢写引擎记忆三件套的隔离机制

> status: approved | scope: engine/decisions/D-029.md, engine/tasks/T-036.md, engine/tasks/T-036.spec.md, engine/tasks/T-036/**, engine/scripts/**, engine/prompts/**, engine/CONTEXT.md, engine/HANDOFF.md, engine/ENGINE_MAP.md, engine/AGENT_ADAPTERS.md, contract/src/**, contract/budget.json, plugin/.claude/**, plugin/engine/**, ENGINE_FILE_SYSTEM_v5.md, AGENTS.md, rules.json | expiry: 2026-11-30(3 个月调研窗口;T-036 已 active,主线方案落地中) | supersedes: none | related: D-025, D-027, D-028, T-032, T-036
> proposed: 2026-07-20 用户报告多 agent 并行执行不同任务卡时,第一个 agent 仍会同时修改引擎记忆三件套(CONTEXT.md / HANDOFF.md / ENGINE_MAP.md),导致三类阻塞:① pre-commit hook 拒绝;② CONTEXT/HANDOFF 被互相覆盖;③ working tree 有 unstaged 脏改动,第二个 agent commit 时只能用 `git add <specific files>` 显式绕过,严重阻塞开发流程。根因疑似:v6.5 workstream 分片 + PreToolUse 拦截"已识别的子 agent"机制只对**同会话派生的 subagent**生效,用户实际开多个**独立顶层 Claude Code 实例**在同一 working tree,这些会话互不识别为 subagent,PreToolUse 拦截失效,每个都按"协调者"协议直接写共享三件套。本决策起草后由 4 路子代理审视决定主线方案,再批准落地。
> revised: 2026-07-20 4 路子代理审视后落实必须改 5 项 + 应该改 4 项 + 5 项固有边界。审视揭示 3 处 D-029 原始措辞过度乐观(§3「不破坏 v6.5 协议」应修订为「扩展触发点 + 新增角色判定机制」;§6 路线 2「怎么生成 session_id」是误解——Claude Code 已传入 session_id,Stop hook 已在用,只需 SessionStart hook 复用;§Consequences 缺 D-028 三文件写入边界与 fail-open/closed 边界)。4 路结论一致:**主线方案 A 可行,需修订**。

## Decision

1. **承认 v6.5 workstream 机制对"同目录多 Claude Code 实例"场景存在覆盖盲区**——现有 PreToolUse 拦截依赖"会话内派生 subagent"的元信息,Claude Code 启动多个独立顶层会话时,这些会话互相看不到对方的 session/agent_id,Stop hook 的归属账本也无法跨进程同步。这不是 v6.5 设计缺陷(其原始目标就是同会话 subagent 隔离),而是用户实际使用模式超出设计假设。本决策**不撤销 v6.5 workstream 机制**,只补"多顶层会话"场景的盲区。

2. **推荐主线方向(4 路审视后定锚):多会话锁 + 第二个会话自动降级为 worker 模式**——
   - SessionStart hook 复用 Claude Code payload 已传入的 `session_id`(Stop hook 已在用,见 `engine-hook-stop.sh:191-197`),不重新生成
   - SessionStart hook 在 working tree 根生成 lock file `engine/.cache/session.lock`,格式 `<pid>|<session_id>|<role>|<started_at_iso>|<task_id>`(单行 pipe-separated,与 .cache/sessions/ 风格一致)
   - 第一个会话用 atomic 操作独占创建 lock(noclobber on POSIX / `FileStream(FileShare.None)` on Windows),获得"协调者"角色(写权限),可写共享三件套
   - 后续会话 SessionStart 检测到 lock 已存在且 pid 存活(双信号:pid + StartTime 比对,防 pid 复用),自动进入 worker 模式,跑 `engine workstream T-NNN <session-id> --kind=session` 写 `engine/workstreams/<task>/<session-id>/` 隔离分片
   - 协调者会话结束时(Stop hook 或进程退出)释放 lock;下一个会话 SessionStart 可接任协调者
   - 协调者僵死时:① 自动检测——pid+StartTime 比对(95%+ 覆盖);② 用户显式接管——`engine assume-coordinator [--force]` 强制覆盖 lock,写 tombstone 文件 `engine/.cache/session.tombstone`(含被接管 session_id + 时间戳)通知其他会话

3. **痛点对应表(4 路审视后修订覆盖率,分档精确化):**
   | 用户痛点 | 机制 | 预期覆盖率 |
   |---------|------|-----------|
   | pre-commit hook 拒绝(无共享记忆或 worker 分片) | worker 模式自动写 `engine/workstreams/<task>/<session-id>/`,pre-commit 接受分片作为合法回写(正则 `engine/workstreams/[^/]+/[^/]+/(CONTEXT\|HANDOFF).md` 已存在) | **是**(C 档)/ **是**(B 档 pre-commit 兜底) |
   | CONTEXT/HANDOFF 被互相覆盖 | 只有持锁协调者可写共享三件套,worker 写分片;PreToolUse 拦截扩展为双信号(`agent_id` 非空 **或** `.cache/sessions/<key>.role=worker`) | **是**(C 档)/ **部分**(B 档无运行时拦截,仅 pre-commit) |
   | working tree 有 unstaged 脏改动 | worker 模式只动自己的 `engine/workstreams/<task>/<session-id>/` 目录,不污染 working tree 根的共享文件(注:worker 改自己的任务卡仍会产生 unstaged 改动,但这是合法任务级改动,与共享三件套污染不同) | **是**(C 档共享三件套)/ **是**(B 档 pre-commit 拒绝共享三件套 staged) |
   | 协调者僵死导致 lock 不释放 | pid+StartTime 比对(95%+ 覆盖)+ `engine assume-coordinator --force` 接管 + tombstone 通知 + kill switch(AC-17) | **部分**——Windows pid 复用 + 任务管理器 kill 后 100% 自动恢复做不到,需用户显式接管或 kill switch |
   | 跨 CLI 适配器覆盖(C 档 Claude Code 机器强制 / B 档 Codex/Cursor/Aider pre-commit 兜底 / A 档与 Web 端纯协议层) | 见上述各行分档覆盖;C 档 lock+PreToolUse 双信号,B 档用户手动 workstream+pre-commit,A 档/Web 端 AGENTS.md 强约束 | **分档**(见 §8 第 6 项 C 档扩展) |

4. **明确不做的(对照原提案,4 路审视后修订):**
   - 不撤销 v6.5 workstream 机制——其原始目标(同会话 subagent 隔离)在该场景仍有效。**审视后修订措辞**:主线方案不是"扩展触发点",而是"扩展触发点 + 新增角色判定机制"——PreToolUse 拦截信号从单信号(`agent_id` 非空)扩展为双信号(`agent_id` 非空 **或** `.cache/sessions/<key>.role=worker`),这是机制扩展不是配置开关
   - 不强制每会话用 git worktree——worktree 物理隔离是另一条路径,适合"不同任务卡大改不同模块"的场景,不适合"同仓多 agent 共享任务上下文"场景;作为可选工作流保留(§6 备选方案 A)
   - 不把 CONTEXT.md / HANDOFF.md 改为 gitignore + sync 命令——破坏可追溯性,CONTEXT 是项目级记忆不是会话本地;作为备选方案在 §6 列出
   - 不引入跨进程分布式锁服务(redis / etcd / 文件服务器)——违反 CLI-LEAN(纯 markdown + shell 脚本,无外部依赖);lock file 用本地文件系统
   - 不让协调者"批量代理所有 worker 提交"——worker 自己提交自己的任务卡 + 分片,协调者只写共享三件套;避免单点阻塞
   - 不引入"自动 merge worker 分片到共享记忆"——merge 仍是显式步骤,由协调者跑 `engine merge-workstream <session-id>` 或读 `engine context` pending 分片后人工合并;自动 merge 风险过高(语义冲突)

5. **备选方案(若主线方案在 4 路审视后被否决):**
   - **备选 A:git worktree 物理隔离工作流**——每个并行任务卡跑在独立 worktree,CONTEXT/HANDOFF 天然隔离,通过 PR/merge 合并。优点:零 hook 改动;缺点:UX 摩擦大(用户要切目录),与"同 working tree 共享任务上下文"的协作模式冲突
   - **备选 B:CONTEXT/HANDOFF 拆为共享基线 + 会话本地增量**——`engine/CONTEXT.md` 只保留"已 merge 的基线状态";会话本地写 `engine/.cache/session-<id>/CONTEXT-delta.md`;显式 `engine merge-session <id>` 合并。优点:天然隔离;缺点:改造面大,改契约,影响所有 agent 适配器
   - **备选 C:纯协议层(无 hook)**——把"多会话场景必须各自跑 engine workstream"写进 AGENTS.md 强约束,pre-commit 兜底。优点:零代码;缺点:依赖 agent 自觉,与 D-025"机器强制不依赖自觉"精神冲突
   - **备选 D:推后到 D-030 / 拆分**——若 4 路审视发现主线方案在 Windows 跨进程同步有不可解决障碍,推后到独立决策 D-030 重新设计

6. **4 路子代理审视计划(类似 D-028 的 6 份审视,4 路适合本问题规模):**
   - **路线 1:hook 跨进程同步可行性审视**——lock file 在 Windows / Linux / macOS 的可靠性;pid 存活检测在 Windows 的固有边界(tasklist vs /proc/<pid>);pid 复用风险;flock / fcntl vs PowerShell New-Object System.IO.FileStream Exclusive;并发竞态窗口;lock 文件残留时的恢复策略
   - **路线 2:多会话 ID 检测与归属账本审视**——(§8 修订:不需重新生成,Claude Code 已传入)原审视问题"怎么生成稳定的 session_id"已被审视结论否定,实际只需 SessionStart hook 开始读取并使用 Claude Code payload 中的 session_id;剩余审视:Stop hook 归属账本如何扩展到"多顶层会话"(实际账本已每会话本地,只需新增 .meta 文件);`engine context` 如何展示当前活跃会话列表 + 各自角色(协调者 / worker)
   - **路线 3:对现有 v6.5 workstream 机制的兼容性审视**——主线方案不能破坏现有 subagent 场景的 workstream 协议;worker 模式的 session_id 与 subagent 的 agent_id 如何区分(避免归档/合并时混淆);现有 `engine workstream T-NNN <agent-id>` 命令是否需要扩参(加 --coordinator / --worker 标志)
   - **路线 4:跨 CLI 适配器可行性审视**——Claude Code 有 PreToolUse / Stop hook 可机器强制;Codex / Cursor / Aider / Web 端无 hook,只能靠 SessionStart + pre-commit 兜底;主线方案在不同适配器下的降级路径;与 AGENT_ADAPTERS.md A/B/C 三档的对应关系

   每路审视产出:必须改 N 项 + 应该改 N 项 + 不改的固有边界。审视后修订本决策覆盖率声明与 expiry。

**关键洞察(审视揭示的误解与修订):**

1. **session_id 不需要重新生成**——Claude Code 已通过 hook payload 传入 `session_id`(Stop hook 在 `engine-hook-stop.sh:191-197` 已在用),SessionStart hook 完全未使用。路线 2 的"怎么生成稳定的 session_id"是误解,实际只需"SessionStart hook 开始读取并使用 Claude Code 提供的 session_id"

2. **归属账本已是每会话本地**——D-029 §6 担心的"共享账本抢写"不存在。现有 `.cache/sessions/<session_key>.paths` 文件名已用 session_id 隔离,每个会话写自己 session_key 的文件,零抢写。只需新增 `.meta` 文件(单行,角色 + 时间戳)

3. **PreToolUse 拦截信号必须扩展**——现有 `[ -n "$agent_id" ]` 单信号对多顶层会话失效(顶层会话的 agent_id 为空)。必须扩展为双信号:`[ -n "$agent_id" ] || [ -n "$ENGINE_SESSION_ROLE" -a "$ENGINE_SESSION_ROLE" = "worker" ]`,角色来源是 SessionStart hook 写的 `.cache/sessions/<session_key>.role=worker` 文件

4. **D-028 LPHP 三文件在 worker 模式下的写入边界必须明确**——D-025 v6.5 落地时 progress.md / INVENTORY.md / checkpoint.md 还不存在,worker 写入边界清单未覆盖。D-028 T-032 落地后若 T-036 未落地,多会话并行时 progress.md 抢写会立即出现。**写入边界方案**(路线 3 给出):
   | 文件 | worker 模式写入位置 | 协调者 merge 时 |
   |------|---------------------|-----------------|
   | progress.md(T-032) | `engine/workstreams/<task>/<session-id>/progress.md`(分片副本,7 栏结构同共享版本) | 读所有 worker 分片,§3/§5/§6/§7 按时间序追加合并;§1/§2/§4 由协调者重写 |
   | INVENTORY.md(T-033) | **不写**(worker 在分片 HANDOFF.md 的 "Merge Notes" 段记录"涉及哪些 INVENTORY entry / Feature 名 / Entry file 路径") | 协调者读 worker 分片 Merge Notes,按 entry 合并到 `engine/domains/<domain>/INVENTORY.md`;merge 后跑一次 Doctor |
   | checkpoint.md(T-034) | `engine/workstreams/<task>/<session-id>/checkpoint.md`(分片副本,AC 状态表) | 读所有 worker 分片,按 AC-id 合并状态;冲突 AC(同 AC 不同状态)由协调者人审 |

5. **fail-open vs fail-closed 边界必须显式声明**——lock file 机制本身 fail-open(老项目不强制 worker 模式);**新项目(contract-version ≥ 6.11.0)的 worker 角色检测必须 fail-closed**(SessionStart 读到 lock 存在且 pid 存活时,本会话必须降级为 worker);若 SessionStart hook 异常失败,fail-open 走单会话路径但 Doctor 输出 WARN("SessionStart hook 异常,多会话隔离失效")

6. **AGENT_ADAPTERS.md 不新增 D 档,作为 C 档扩展子段**——多会话锁是 hook 触发机制扩展,与 C 档"原生 hook 触发"同质,不属于新能力档位;新增 D 档会让"档位"概念膨胀(横切 concern,不是能力梯度)。B/A 档在表格里注明"不支持自动 lock 检测,降级为单会话或手动 workstream"

7. **migrator 与 contract-version 升级**——引入版本 v6.11.0(假设);老项目(< 6.11.0)SessionStart 检测到 lock 仅 WARN 不强制 worker(fail-open);新项目(≥ 6.11.0)强制 worker(fail-closed)。与 D-028 §9 范式对齐

8. **新增两个命令**——`engine assume-coordinator [--force]`(强制接管)+ `engine merge-workstream <session-id>`(显式 merge worker 分片到共享记忆)。两者都是 hook 自动检测之外的逃生通道,符合"机器强制 + 用户显式接管兜底"原则

9. **workstream 命令加可选 `--kind=subagent|session` 参数**(默认 `subagent` 向后兼容)+ `s-`/`a-` 命名前缀约定(人类可读视觉提示)——双轨制机器识别 + 视觉识别

10. **改造面修订**(对比原 §Consequences 估计):
    - 原估:≤150 行 sh + ≤150 行 ps1 + ≤80 行文档
    - 修订后:sh ~80 行(SessionStart 30 + Stop 15 + context 25 + workstream 迁移 10)+ ps1 ~80 行 + 文档 ~50 行(AGENT_ADAPTERS 多会话档位 + ENGINE_DOCTOR workstream 孤儿检查 + GLOSSARY session_id/agent_id 条目)
    - **总计 ≤210 行,略低于原估**

## Consequences

- **常驻上下文增量:** SessionStart hook 多读 lock file 1 行(协调者标志)或 1 段(worker 模式提示,≤3 行),不进 SessionStart 全文;`engine context` 新增"Active Sessions"面板插入在"Active Task Card"与"Parallel Workstreams"段之间(≤5 行/会话,每行 ≤61 chars 适配 PS 5.1 buffer);总量 ≤30 行,符合 N1 ≤400 预算。无活跃会话时不输出该段,保持现状
- **强制力升级:** 主线方案引入"会话角色"概念(协调者 / worker),由 hook 机器分配,不依赖 agent 自觉声明;worker 模式下写共享三件套由 PreToolUse 双信号拦截(C 档)或 pre-commit 兜底(B 档);新项目(contract-version ≥ 6.11.0)fail-closed,老项目 fail-open 与 D-028 §9 迁移宽限期范式一致
- **复杂度上升:** 新增 lock file(`engine/.cache/session.lock`,已被 .gitignore 第 2 行 `engine/.cache/` 覆盖,天然不进 git);新增 tombstone 文件(`engine/.cache/session.tombstone`);新增 kill switch 标志文件(`engine/.cache/multi-session.disabled`)+ 环境变量 `ENGINE_DISABLE_MULTI_SESSION=1`(T-036 AC-17);新增 `engine assume-coordinator [--force]` 与 `engine merge-workstream <session-id>` 与 `engine disable-multi-session` 三个命令;SessionStart / Stop hook 改造(双份 sh+ps1);`engine context` 扩展活跃会话面板;`engine workstream` 加 `--kind` 参数;AGENT_ADAPTERS.md 加 C 档扩展子段;预算增量 ≤210 行(审视后修订,低于原估 ≤380)
- **kill switch 逃生通道:** 若 v6.11.0 上线后 lock 机制有 bug 阻塞所有并行开发,用户可设 `ENGINE_DISABLE_MULTI_SESSION=1` 环境变量或跑 `engine disable-multi-session` 命令,SessionStart hook 跳过 lock 检测,所有会话降级为单会话模式(等同现状 fail-open)。这是 T-036 AC-17 强制要求的逃生通道,与 fail-open 边界一致
- **与 D-025 的张力:** D-025 v6.5 workstream 的"subagent 识别"是同会话内的,本决策扩展到"多顶层会话";两者不冲突——subagent 走现有 `engine workstream T-NNN <agent-id>` 协议(默认 `--kind=subagent`),顶层会话走新的 lock-based 协调者/worker 分配(`--kind=session`);`agent-id` 与 `session-id` 命名空间隔离(subagent 是同会话内派生,session-id 是顶层会话级);PreToolUse 双信号判定:`agent_id` 非空(subagent) **或** `.role=worker` 文件存在(顶层会话)
- **与 D-027 HANDOFF 历史归档的张力:** 多会话并行时,HANDOFF 历史表仍由协调者一次写;worker 模式下 HANDOFF 历史表不增行(只写自己分片的 HANDOFF);归档触发只在协调者会话执行
- **与 D-028 LPHP 路线的张力(审视后细化):** D-025 v6.5 worker 写入边界清单未覆盖 progress.md / INVENTORY.md / checkpoint.md(D-028 三文件在 v6.5 落地时还不存在)。本决策明确边界:progress.md / checkpoint.md worker 写分片(`engine/workstreams/<task>/<session-id>/` 下),INVENTORY.md worker 不写(在分片 HANDOFF.md Merge Notes 记录变更清单,merge 时由协调者补写共享域文件)。**关键依赖**:T-032(v6.7.0 progress.md)落地后若 T-036(D-029 落地)未落地,多会话并行时 progress.md 抢写会立即出现;建议在 T-032 落地前先打 patch(progress.md 写入路径条件化:检测 worker 模式则写分片)。INVENTORY 与 checkpoint.md 同款逻辑
- **范围诚实:** 主线方案能解决 3 个用户痛点(pre-commit 拒绝 + 互相覆盖 + unstaged 脏改动),对"协调者僵死"是部分覆盖(95%+ 自动检测 + `--force` 兜底);对"跨 CLI 适配器"是分档覆盖(C 档机器强制 / B 档 pre-commit 兜底 / A 档与 Web 端走纯协议层)。Windows pid 复用 + 任务管理器 kill 后 100% 自动恢复做不到,Web 端 AI 不适合多会话并行场景——这是同目录多顶层会话场景的固有边界,不是方案缺陷

## Options Considered

- **A. 多会话锁 + 第二个会话自动降级为 worker(本决策主线推荐)**——hook 检测同 working tree 多活跃会话,第一个当协调者,后续自动降级为 worker 写分片,显式 merge 步骤汇总。优点:对现有 v6.5 协议扩展最小,机器强制;缺点:lock file 跨进程同步在 Windows 有固有边界,需 4 路审视验证可行性
- B. git worktree 物理隔离工作流——每个并行任务卡跑独立 worktree,CONTEXT/HANDOFF 天然隔离,PR/merge 合并。优点:零 hook 改动;缺点:UX 摩擦大,与同仓协作模式冲突
- C. CONTEXT/HANDOFF 拆为共享基线 + 会话本地增量——基线 + delta 模型,显式 merge-session。优点:天然隔离;缺点:改造面大,改契约
- D. 纯协议层(无 hook)——AGENTS.md 强约束 + pre-commit 兜底。优点:零代码;缺点:依赖 agent 自觉,与 D-025 精神冲突
- E. 推后到 D-030 重新设计——若 4 路审视发现不可解决障碍。优点:不冒险;缺点:阻塞用户开发流程(用户已报告"严重阻塞")

## Rationale

用户报告的 3 个阻塞(pre-commit 拒绝 + 互相覆盖 + unstaged 脏改动)是 v6.5 workstream 机制对"同目录多 Claude Code 实例"场景的覆盖盲区导致——现有 PreToolUse 拦截依赖"会话内派生 subagent"的元信息,独立顶层会话互相看不到对方的 session/agent_id。这不是 v6.5 设计缺陷(其原始目标就是同会话 subagent 隔离),而是用户实际使用模式超出设计假设。

主线推荐方案 A(多会话锁 + 自动降级 worker)是因为:
1. 对现有 v6.5 协议扩展最小——worker 模式仍走 `engine workstream` 命令,只是触发点从"subagent 派生"扩展到"多顶层会话锁检测"
2. 机器强制不依赖自觉——lock file 由 SessionStart hook 自动创建/检测,worker 模式由 hook 自动切换,符合 D-025 精神
3. 不破坏可追溯性——共享三件套仍是单一权威源(协调者写),不引入会话本地副本

但 Windows 跨进程同步(lock file + pid 检测)有固有边界,必须经 4 路审视验证可行性后才批准落地。审视发现不可解决障碍时走备选方案 A(git worktree)或 C(delta 模型)。

分阶段(4 路审视 → T-036 任务卡 → pilot → 正式发版)而非一次全上,是因为多会话并行是高风险改造,任一环节失败会阻塞用户所有并行任务。每个阶段独立验证、失败可回退,是 D-026/D-028 发布门精神在并行隔离场景的延伸。

## Open Questions

1. **lock file 跨进程同步在 Windows 的可靠性** ✅ 已回答(路线 1):部分可行。PowerShell `FileStream(FileShare.None)` 提供原子独占创建,OS 保证无 TOCTOU;pid 复用风险通过 `Get-Process.StartTime` 比对缓解(精度到秒,容差 2 秒);任务管理器 kill 后 OS 自动释放句柄,lock 文件可被其他进程删除。但 100% 自动恢复做不到,需 `--force` 兜底
2. **session_id 跨进程唯一性** ✅ 已回答(路线 2):Claude Code 已通过 hook payload 传入 session_id(Stop hook 已在用 `engine-hook-stop.sh:191-197`),**不需要重新生成**。SessionStart hook 只需开始使用 Claude Code 提供的 session_id。非 Claude Code 适配器 fallback 到 UUID v4(PS 5.1 用 `[guid]::NewGuid().ToString()`,Bash 用 `uuidgen` 或 `/proc/sys/kernel/random/uuid`)。命名空间隔离:目录隔离(`engine/workstreams/<task>/sessions/<id>/` vs `engine/workstreams/<task>/agents/<id>/`)+ `s-`/`a-` 前缀约定(双轨制)
3. **协调者僵死的检测与恢复** ✅ 已回答(路线 1):pid+StartTime 比对覆盖 95%+ 场景;极端情况(同秒 pid 复用 + starttime 精度不足)需 `engine assume-coordinator --force` 强制接管,写 tombstone 文件 `engine/.cache/session.tombstone` 通知其他会话。这是"足够好"而非"完美"
4. **跨 CLI 适配器降级路径** ✅ 已回答(路线 4):C 档(Claude Code)机器强制 lock 检测 + PreToolUse 双信号拦截;B 档(Codex/Cursor/Aider)无 SessionStart hook → 用户手动 `engine workstream T-NNN <session-id>` + pre-commit 兜底(拒绝共享三件套 staged);A 档与 Web 端走纯协议层(选项 D)。**不是纯协议层**(B 档有 pre-commit 兜底),与原 D-029 §6 假设不同
5. **progress.md / INVENTORY / checkpoint.md 在 worker 模式下的写入边界** ✅ 已回答(路线 3):progress.md / checkpoint.md worker 写分片(`engine/workstreams/<task>/<session-id>/` 下);INVENTORY.md worker 不写(在分片 HANDOFF.md Merge Notes 记录变更清单,merge 时协调者补写共享域文件)。**关键依赖**:T-032(v6.7.0 progress.md)落地后若 T-036(D-029 落地)未落地,多会话并行时 progress.md 抢写立即出现;建议在 T-032 落地前先打 patch(progress.md 写入路径条件化)
6. **expiry 与 D-028 路线的协调** ✅ 部分回答:D-028 v6.7.0~v6.10.0 已发版完成,本决策走 v6.11.0+ 独立版本号,无版本号冲突。但"D-028 落地后多会话并行痛点是否被放大"由路线 3 揭示:**是**——D-028 三文件在 worker 模式下未规定写入边界,需在 T-036 落地前先打 patch。剩余:D-028 路线若某版本延期,本决策是否要前置(因痛点放大)留给架构师拍板
