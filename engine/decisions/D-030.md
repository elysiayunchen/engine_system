# D-030: Issue #9 修复方案 A+B 批准

> status: approved | scope: install.ps1, plugin/manifest.json, engine/decisions/D-030.md, engine/bin/engine.cmd, plugin/bin/engine.cmd, plugin/engine/bin/engine.cmd, VERSION, engine/VERSION, plugin/VERSION, CHANGELOG.md, engine/tasks/T-042.md, engine/tasks/T-042.spec.md, engine/tasks/T-042/progress.md, engine/archive/tasks/T-042-progress.md, engine/CONTEXT.md, engine/HANDOFF.md, engine/handoff-archive-2026-07.md, engine/ENGINE_MAP.md, engine/changes/CHANGE-2026-07-23-01.md, engine/evidence/T-042/** | expiry: 2026-11-30(保持;patch 修复无硬性到期需求) | supersedes: none | related: T-042, issue #9
> proposed: 2026-07-23 GitHub issue #9 报告 installer 产出 LF-only engine.ps1,PowerShell 5.1 无法解析 here-string(行号错位导致 `}` token 错位)。影响 engine.cmd shim 在仅有 PS 5.1 的 Windows 系统上完全不可用。

## Decision

1. **批准方案 A+B 双保险修复 issue #9**:
   - **方案 A**: `install.ps1` 在 `Download-File` / `Copy-Local` 下载/复制 `.ps1` 文件后,将 LF 转换为 CRLF 写盘。仓库源保持 LF(由 `.gitattributes` 钉 `*.ps1 text eol=lf`,D-015 跨平台一致策略);用户机器侧转 CRLF(PS 5.1 需要 CRLF 正确解析 here-string)。
   - **方案 B**: `engine.cmd` 优先检测 `pwsh.exe`(PowerShell 7),未找到则回退 `powershell.exe`(PS 5.1)。PS 7 解析 LF-only here-string 正确,即使方案 A 失效(如用户 git clone 而非 install)也能兜底。

2. **checksum 兼容性**: `install.ps1` 的 `Get-NormalizedTextSha256`(L83-98)已 strip CRLF→LF 再算 hash,manifest 按 LF 算 SHA256。方案 A 转 CRLF 后写盘,checksum 校验时 strip 回 LF,与 manifest 一致——**无需改 manifest 的 hash 算法或重新签发所有文件**,只更新被改动文件(`bin/engine.cmd`)的 SHA256。

3. **.gitattributes 不改**: 仓库源保持 LF 策略(D-015「钉 dist/src 行尾」决策)。转 CRLF 仅在用户机器侧由 install.ps1 完成,不污染开发仓库。`git clone` 的开发者装了 PS 7 或在 WSL 跑,不受影响。

4. **engine.ps1 here-string 不改**: 字节级分析发现 install.ps1 自己也是 LF-only(LF=464)且用 here-string(L264)却能跑完整个安装,而 engine.ps1(LF=727)有 3 个 here-string(L20/323/351)首个在 L20 极靠前 → 报错。证明 PS 5.1 对 LF-only 文件 here-string 解析的 bug 是**累积性行号错位**(here-string 数量与首现位置决定何时炸),而非 here-string 本身禁用。方案 A 转 CRLF 即根治,无需改 engine.ps1。

## Consequences

- **PS 5.1 用户恢复可用**: engine.cmd shim 在仅有 PS 5.1 的 Windows 系统上恢复可用(方案 A 转 CRLF + 方案 B pwsh 优先双保险)。
- **仓库无影响**: 开发仓库源保持 LF,跨平台 diff 干净,`.gitattributes` 不变。
- **checksum 无影响**: manifest SHA256 算法已 normalize,转 CRLF 不触发校验失败。
- **复杂度微增**: install.ps1 加 ~12 行 LF→CRLF 转换逻辑(Convert-ToCrlf 辅助函数 + Download-File/Copy-Local 调用点);engine.cmd 加 ~3 行 pwsh 检测。

## Options Considered

- **A. install.ps1 转 CRLF + engine.cmd pwsh 优先(本决策选定)**——双保险,根治 + 兜底。
- B. 只改 engine.cmd pwsh 优先——绕过而非根治;用户无 PS 7 时仍炸(issue 列为备选 2)。
- C. 只改 install.ps1 转 CRLF——不兜底 git clone 场景;但 issue 场景是 install.ps1 -Update,覆盖。
- D. 去 here-string——install.ps1 自己用 here-string 能跑通,证明非必要;治标不治本(issue 列为备选 3)。
- E. 改 .gitattributes 把 *.ps1 钉 CRLF——破坏跨平台一致性,D-015 决策回退。

## Rationale

issue #9 根因双重作用:(a) PS 5.1 对 LF-only 文件 here-string 解析有累积性行号错位 bug(engine.ps1 有 3 个 here-string 首个在 L20,install.ps1 仅 1 个在 L264 故能跑完);(b) engine.cmd L4 写死 `powershell` 无 pwsh 检测。方案 A 治 (a),方案 B 治 (b),双保险。仓库保持 LF 策略不变(D-015),转 CRLF 仅在用户机器侧完成。`Get-NormalizedTextSha256` 的 strip-CRLF 设计已为换行符差异预留兼容,无需改 manifest 算法。

## Watchpoints

- 若用户通过 `git clone` 而非 `install.ps1` 获取仓库,engine.ps1 仍是 LF-only,方案 A 不生效——但方案 B 的 pwsh 优先检测兜底(前提:用户装了 PS 7)。纯 PS 5.1 + git clone 场景需文档提示走 install.ps1。
- 若未来 engine.ps1 新增更多 here-string,方案 A 转 CRLF 仍根治(只要写盘是 CRLF,PS 5.1 解析正常)。
- 若 PS 7 在未来 Windows 版本成为默认,方案 B 的 fallback 逻辑可简化为直接 pwsh。
