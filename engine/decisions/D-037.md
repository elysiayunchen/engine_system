## Background — 问题实证(2026-07-29)

issue #13 [D-11] 报告 pre-commit hook + doctor 的 AC parser 只识别第 1 种格式,导致 4 张 done 卡被误报 "no declared AC" FAIL:

| 格式 | 语法样例 | 当前识别 |
|------|---------|---------|
| 1. 单行 | `AC: AC-N \| verify: <cmd>` | ✓ |
| 2. 章节标题 | `### AC-N: <title>` + body 含 `verify: <cmd>` | ✗ |
| 3. 列表项 | `- AC-N: <description>` + 同/下行 `verify: <cmd>` | ✗ |
| 4. 表格行 | `\| AC-N \| verify: <cmd> \|` | ✗ |

核查证据(子代理 5 维度):
- `engine-doctor.sh:1258` / `engine-doctor.ps1:1252`:`sed -n 's/^AC:[[:space:]]*\(AC-[0-9][0-9]*\).*/\1/p'` 行首锚定 `^AC:`,只取 AC id。
- `githooks/pre-commit:281`:同上正则。
- `engine-verify.sh:347-352` / `engine-verify.ps1:386-391`:报错文案显式承认 "only reads single-line 'AC: AC-N ... | verify: <cmd>'"。
- v6.12.1 (issue #11 / T-049) 已在 `CHANGE-2026-07-26-03.md:64,69` 把这块**显式推迟**为后续工作。
- unified task-card field parser(`Get-TaskPatterns` / `parse_task_patterns`,v6.12.1 issue #11 B-1)只覆盖 WRITE-SET 和 FORBIDDEN,**不覆盖 AC**(因 AC 需返回 (id, verify) 对,unified parser 返回逗号分隔串,返回类型不匹配)。

## Decision

契约版本 **v6.17.0**(minor bump,因契约 src 变更)。核心原则:**解析器全 4 格式的读兼容,写入器仍只写第 1 种格式(规范格式),不强制改写老卡。**

### D1:4 种合法 AC 声明格式(契约 + 解析器对齐)

| # | 名称 | 语法 | verify 命令抽取 |
|---|------|------|----------------|
| 1 | 单行(规范) | `AC: AC-N <description> \| verify: <cmd>` | 同行 `verify:` 后到行尾 |
| 2 | 章节标题 | `### AC-N: <title>` + 紧跟 bash 代码块首行 / 紧跟段落 `verify: <cmd>` | 章节体内首个 `verify:` 行 |
| 3 | 列表项 | `- AC-N: <description>` + 同行 `\| verify: <cmd>` 或下一行 `  verify: <cmd>` | 同行优先,否则下一行 |
| 4 | 表格行 | `\| AC-N \| <description> \| verify: <cmd> \|` | 第 3 列 `verify:` 后到 `\|` 前 |

**约束(共通):**
- AC id 正则:`AC-[A-Za-z]*\d+(?:\.\d+)*`(复用 v6.12.1 A-3 放宽)
- verify 命令界定符:`| verify:` 或 `→ verify:` 或行首 `verify:`(复用 v6.12.1 A-2)
- 同一卡可混用 4 种格式(每条 AC 用任意一种)
- 一条 AC 在卡内只能声明一次(重复以首次为准,WARN 第二次)

### D2:解析器实现 — 新增 `parse_ac_declarations` 函数(不复用 unified field parser)

unified parser 返回逗号分隔 glob 串,无法表达 (ac_id, verify_cmd) 对。**新增专用函数** `parse_ac_declarations(file)`,返回 `\n` 分隔的 `<ac_id>\t<verify_cmd>` 列表。

实现站点(6 处,每处 sh+ps1 = 12 份,加 plugin 镜像 = 24 份副本):
1. `engine/scripts/engine-verify.sh` + `.ps1`(verify 主入口)
2. `engine/scripts/engine-doctor.sh` + `.ps1`(替换 L1258 / L1252 窄正则)
3. `engine/scripts/githooks/pre-commit`(替换 L281 窄正则)
4-6. 对应 `plugin/engine/scripts/` × 3 份镜像(byte-identical)

### D3:契约变更点

- `contract/src/00-core.md` §84 Behavior Verification Rule:扩写「AC 与 verify 命令必须同行」为「AC 与 verify 命令可在同行,或在 `### AC-N:` 章节体内,或列表项/表格行配对(见 20-file-templates FILE NN)」。
- `contract/src/20-file-templates.md` FILE 15(任务卡模板):列出 4 种合法格式最小示例。

### D4:行为兼容与回归

## Rationale

- **为什么不只迁移老卡(issue 备选方案)**:4 张老卡是下游项目实证,本仓也有同类卡。每次新卡风格漂移都会再触发,根因是 parser 太窄。
- **为什么不复用 unified parser**:返回类型不匹配(逗号分隔串 vs (id, verify) 对)。强行复用需改 unified parser 的 API,影响 WRITE-SET/FORBIDDEN 的 5 个调用点,风险大于收益。
- **为什么写入器不写多种格式**:第 1 种单行格式最易解析、最紧凑、最易 grep;其它 3 种是「读兼容」让历史卡和不同作者风格可共存,不是「写鼓励」。
- **为什么契约 minor bump**:契约 src 改了(00-core + 20-file-templates + verify-writeback),按 D-026 发布门规则需 minor bump。

## Non-goals

- 不做 AC 格式自动迁移(老卡保留原格式,parser 兼容读)。
- 不引入 AC 格式 linter(不做"建议改用单行格式"WARN)。
- 不支持代码块外的多行 verify 命令(verify 命令必须单行,符合现状)。
- 不改 unified task-card field parser 的 API(只在 AC parser 内部实现 4 格式逻辑)。
