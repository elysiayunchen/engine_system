## Background — 漂移实证(2026-07-30)

当前 evidence 结构(`engine/evidence/T-065/AC-1.json`):

```json
{"ac":"AC-1","verify":"bash -c \"grep ...\"","status":"pass","exit":0,
"fingerprint":"sha256:5993cb...","timestamp":"2026-07-30T08:17:51Z"}
```

**`fingerprint` 是 verify 命令输出的 sha256,不是被验证代码内容的 sha256。** 这决定了 5 类漂移,每类对应一个已存在缺口:

| 类型 | 触发场景 | 当前缺口 |
|------|----------|----------|
| 时间漂移(regression) | done 时为真,后续代码被改导致不再为真 | evidence 一次性快照,SessionStart/pre-commit/Doctor 都不重跑 |
| 锚点漂移 | verify 通过但验证的不是真 AC | fingerprint 锚输出非代码,v6.12.1 tautology WARN 只抓空输出 |
| 声明漂移 | CONTEXT/MAP 写"已完成"但代码已回退 | 状态面板纯人工声明,无机器校验 |
| 状态漂移 | 任务卡 done 但 evidence 与代码脱节 | pre-commit 只查 evidence 文件**存在**,不校验**一致** |
| 决策漂移 | approved 决策被当成"已落地" | D-xxx approved ≠ 已实施,CONTEXT 无区分 |

记忆已记录同根因:"CONTEXT.md「上次完成」面板栈式插入、从不修剪" + "HANDOFF.md 立即恢复点执行不严"——声明漂移的温床。

## Design Principle

> 凡是 agent 会读作"已落实"的声明,必须是「可派生视图」或带「连续不变量」;不可机器校验的声明,必须显式标注为未验证。把"声明状态"与"事实状态"从「一次性绑定 + 之后解耦」升级为「持续绑定」。

## Decision — 4 层防漂移

### D-038a · 证据多锚 + 完整性自证(根治时间漂移 + 锚点漂移 + evidence 篡改)

evidence schema 从单 fingerprint 升级为多锚 + 自证完整性。**关键修正(复审 P0-2):哈希算法用 `git ls-files -s <path>` 取 index blob sha,而非 `git hash-object`/`sha256sum`/`Get-FileHash`——`git hash-object` 对未 staged 的工作树文件算原始字节(含 CRLF),与 `sha256sum` 无本质区别;`git ls-files -s` 取的是 index 里已 EOL 归一化的 blob sha(归一化发生在 `git add`,由 `.gitattributes` 控制),跨平台一致。前置要求:WRITE-SET 文件必须先 `git add`(verify 命令前置检查,未 add 则 FAIL 提示)。**

字段:

- `output_fingerprint`: verify 命令输出 sha256(现有 `fingerprint` 改名,向后兼容)
- `code_fingerprint`: 新增,被验证代码文件的 `git ls-files -s <path>` 结果字典(取 index blob sha,已 EOL 归一化),path 来自任务卡 WRITE-SET 中**非 engine 元数据**文件(代码/测试/脚本)。sh/ps1 均调用 `git ls-files -s`,跨平台一致。不用 `git hash-object`(未 staged 时算原始字节)/`sha256sum`/`Get-FileHash`(算工作树字节)。**前置:文件须 `git add` 进 index**,verify 命令检查未 add 则 FAIL 提示
- `write_set_snapshot`: 新增,verify 时刻任务卡 WRITE-SET 的快照(原文 path 列表),供 D-038b 检测 WRITE-SET 二阶漂移
- `verified_against_commit`: 始终是 verify 时刻 `git rev-parse HEAD`(与文件是否在 HEAD 无关,新卡首次 done 时 HEAD 仍有效)
- `evidence_manifest_sha256`: 新增,`engine/evidence/T-NNN/` 目录下所有 `.json` 文件(含 AC-*.json + DEAD-CODE.json + COPY-PASTE.json + checkpoint.md,**排除 MANIFEST.json 自身**,否则鸡生蛋)sha256 的聚合 hash。聚合规则:按文件名字典序排序(跨平台一致),每行 `<filename>:<sha256>` 拼接,对拼接结果算 sha256。由 `engine verify` 写入 `engine/evidence/T-NNN/MANIFEST.json`。drift-check 第一步校验它——**evidence 被直接 Edit 篡改 code_fingerprint 时,manifest 不一致 → FAIL "evidence tampered",不进入后续比对**
- `write_provenance`: 新增,记录 evidence 写入来源:`{"writer":"engine-verify","commit":"<sha>","timestamp":"<iso>","argv":"engine verify T-NNN"}`。由 `engine verify` 自动写入;**手动 Edit 无法伪造合法 provenance**(pre-commit 校验 provenance.writer 必须为 `engine-verify` 且 commit 与当前 HEAD 一致,否则视为篡改——见 D-038d 决策点 #7 定论)

兼容:旧 evidence 缺新字段时按单锚处理(只做 output 比对,信任级标 T2);旧 evidence 不强求回填,迁移期策略见 D-038d。

**evidence 完整性门禁(三道)**:`engine/evidence/**` 现非 protected_paths(rules.json L3-15)且被 ENGINE_MAP.md:68 归为 generated-cache——agent 可一行 Edit 绕过。本决策要求:

1. `engine/evidence/**` 纳入 `rules.json` protected_paths(改它需 approved 决策覆盖)
2. `engine verify` 自动重算 MANIFEST.json + 写 write_provenance
3. Doctor + pre-commit 校验 MANIFEST 一致 + provenance 合法(详见 D-038d #7 定论)

### D-038b · 连续不变量校验(根治状态漂移 + WRITE-SET 二阶漂移)

新增 `engine drift-check` 命令(Doctor 集成),**不重跑 verify**,只做廉价指纹比对。**关键修正(评估 P1-3/P1-4):drift-check 撤出 pre-commit——hook 已 L400+ 过载且 staging 语义模糊;只在 Doctor / `engine drift-check` 手动 / SessionStart 三处触发。**

执行顺序(三步,**任一步 FAIL 仍输出后续摘要,避免 manifest 失败掩盖更深的代码漂移**):

1. **完整性自证(堵篡改)**:重算 `engine/evidence/T-NNN/MANIFEST.json` 的聚合 hash,与 evidence 中声明的 `evidence_manifest_sha256` 比对;同时校验 `write_provenance.writer=engine-verify` 且 `commit` 与当前 HEAD 一致。不匹配 → `FAIL: T-065 evidence tampered (manifest mismatch or invalid provenance)`。**FAIL 后仍输出后续两步摘要(标"unverified, manifest 失败")**,让架构师知道"可能有更深的漂移"
2. **WRITE-SET 二阶检测(评估 P1-3)**:比对 evidence 的 `write_set_snapshot` 与当前任务卡 WRITE-SET。增删路径 → `WARN: T-065 WRITE-SET changed since evidence (added: X, removed: Y)`。**只 WARN 不 FAIL**——合法的 WRITE-SET 扩展存在(如补漏路径);但让架构师可见二阶改动,防止追溯扩大 code_fingerprint 范围掩盖漂移
3. **代码指纹比对**:重算 `code_fingerprint` 里每个文件的当前 `git ls-files -s <path>`,与存储值比对。不匹配 → `DRIFT: T-065 AC-1 code changed since evidence (commit 93aaa90 → HEAD)`;`verified_against_commit` 与 HEAD 比对,报告"自校验以来 N 个 commit 改动了被验证代码"。**文件已被删除时**:`git ls-files -s` 返回空 → `DRIFT: T-065 AC-1 file deleted (path: X)`

触发时机(三处,**不含 pre-commit**):

- `engine doctor`:全量 done 卡(成本可控,非交互)
- `engine drift-check` 手动:全量或 `--task T-NNN` 单卡
- SessionStart:仅查 federation.json 当前域路由到的 done 卡 + mtime 缓存(文件 mtime 未变则跳过 hash 重算,Windows `Get-FileHash` 单次 30-80ms × 500 文件 = 15-40s 不可接受,缓存后通常 <1s)

**自举说明(评估边界 case 1,复审必改 #1 修正)**:`engine/scripts/engine-drift-check.{sh,ps1}` 属 engine 元数据,**排除出 code_fingerprint**(否则改脚本让所有 done 卡假 DRIFT)。脚本自身的完整性由两层管:

1. **本决策要求 `engine/scripts/engine-drift-check.{sh,ps1}` 显式加入 `rules.json` protected_paths**(实施时与 `engine/evidence/**` 同批加入)。**复审 #1 发现:`rules.json` L3-15 现不含 `engine/scripts/**`,本卡之前的"已受 protected-path 门禁"论断是假的**——必须本决策实施时显式加入,否则 agent 可自建 active 卡覆盖改 drift-check 脚本让它永远返回 PASS,无任何门禁
2. 改 drift-check 脚本需 approved 决策覆盖(scope 含 `engine/scripts/engine-drift-check.*`,本卡 scope L3 已声明)

**删除原误用的 dist-stale 论断**:复审发现 T-051 dist-stale 校验的是 contract 编译产物(6 个 dist 文件)与 `contract/src/**` 源一致,**不校验 drift-check 脚本本身**——dist-stale 不能作为 drift-check 脚本完整性保护。drift-check 脚本的 plugin 镜像(`plugin/engine/scripts/engine-drift-check.*`)由既有 mirror-parity 检查管(若存在),不在本决策新增范围。

不引入"校验校验器"无穷回归:protected_paths 改 drift-check 脚本需 approved 决策,决策批准流程是人工环节,够用。

**并发说明(D-035 多卡并行)**:drift-check 只读不写,假 DRIFT 不破坏数据;但对"刚改过的文件"(mtime < 60s)输出 WARN 而非 FAIL,避免另一会话中间状态误报。

**循环依赖(评估边界 case 2)澄清**:无真环。流向为 任务卡 status → drift-check(输入)→ evidence(快照,只读)→ 当前文件(磁盘状态);CONTEXT 派生视图读 drift-check 结果但 drift-check 不读 CONTEXT。隐耦合:任务卡 status 被改回 `active` 则 drift-check 不再查该卡——这归"任务卡 status 篡改"漂移,由 protected_paths + 决策覆盖门禁管,不属 D-038 范围。

### D-038c · 状态面板视图化(根治声明漂移)

CONTEXT.md / ENGINE_MAP.md 状态面板从**权威声明**降级为**派生视图**:

- "上次完成 v6.17.4" ← 派生自 `git tag v6.17.4` 存在 + `engine/VERSION=6.17.4` + T-065 status:done + 该卡 evidence 无 DRIFT
- 里程碑 ✅ ← 派生自对应 tag + verify 全绿 + drift-check 通过
- 人工只写**决策与意图**(本轮拍板、待验证),不写**事实状态**
- 实现:状态面板段加 `<!-- derived: git-tag + engine/VERSION + evidence-drift -->` 标注;`engine context` 输出时实时重算该段而非读静态文件;Doctor 对"derived 段无标注"或"标注源与实际不符"FAIL

### D-038d · 信任分级注入(根治决策漂移 + agent 误判)

`engine context` 输出时给每条声明打信任级别:

- **T1 机器校验通过**:evidence 有 code_fingerprint + 无 DRIFT + tag/VERSION 一致 + drift-check 绿 → agent 可当"已落实"下结论
- **T2 声明但未校验**:无 code_fingerprint 的旧 evidence、人工写的状态、`approved` 决策 → agent 须说"据声明 X,但未机器校验"
- **T3 待验证**:明确标注 unverified → agent 须先跑校验或显式声明"未验证"
- 反向追溯:每个 commit 已有 task ID(pre-commit decision reference 扩展),`git log` 能回答"这个文件最后被哪个任务改、那个任务 done 了吗、evidence 还有效吗"——闭环

**迁移期方案(评估 P2-5,堵 T2 通胀)**:旧 evidence 不一律降 T2,而是分档:

- 有 code_fingerprint 且 drift-check 绿 → **T1**
- 无 code_fingerprint → **T2**(标 `legacy-evidence,未补 code_fingerprint`)
- 人工声明/approved 决策 → **T2**(标 `declared-only`)

T-NNN 实施时对 ENGINE_MAP.md 列出的近期 done 卡(T-048~T-065,14+ 张)批量重跑 `engine verify T-NNN` 补 code_fingerprint,目标:90% 近期 done 卡升 T1。深度历史卡(更早)可保留 T2,不影响日常 agent 判断。

**与 D-019e 预算关系(评估兼容性 #4,修正"正交"论断)**:不严格正交。T1/T2/T3 标签注入 `engine context` 输出,每条声明多 4-6 字符 × N 行。若 CONTEXT 有 30 条声明,增加约 120-180 字符。**本决策声明:标签注入计入 D-019e SessionStart 预算,从别处省**(如 HANDOFF 历史裁剪已省出空间)。D-019e 的"≤400 行"硬上限优先,T-NNN 实施时若超预算,优先压声明条数而非砍标签——标签是分级的载体,砍了等于废 D-038d。

**决策点 #7 定论(复审必改 #3,verify 写 evidence 是否豁免 protected_paths)**:

**定论:verify 豁免 + write_provenance 标记 + pre-commit 校验 provenance 合法性。** 不再遗留到 T-NNN。

机制:

- `engine verify T-NNN` 写 evidence 时,自动在每个 AC-*.json + MANIFEST.json 写入 `write_provenance` 字段(D-038a 已声明):`{"writer":"engine-verify","commit":"<git rev-parse HEAD>","timestamp":"<ISO>","argv":"engine verify T-NNN"}`
- pre-commit hook 检测 staged 含 `engine/evidence/**` 时:
  - **每条 AC-*.json / MANIFEST.json 必须有 `write_provenance` 字段**——缺失 → FAIL "evidence modified without provenance (manual Edit suspected)"
  - **`provenance.writer` 必须为 `engine-verify`**——其他值 → FAIL
  - **`provenance.commit` 必须等于当前 `git rev-parse HEAD`**——不匹配 → FAIL "evidence provenance commit mismatch (stale or tampered)"
  - **`provenance.argv` 必须匹配 `engine verify T-NNN` 模式**——异常 → FAIL
- **三处一起改攻击(复审 P0-1 残留)防御**:agent 改 code_fingerprint + 重算 MANIFEST + 改 provenance 字段三处一致,仍能绕过——**但 provenance.commit 必须等于当前 HEAD**,而 HEAD 是上一次 commit 的 sha,agent 无法伪造"这次 evidence 是过去某 commit 时 verify 写的"而不被 HEAD 校验发现。唯一攻击窗口:agent 在当前 HEAD 下跑 `engine verify` 重算(合法)+ 同时改 code_fingerprint(非法)——这种"verify 调用期间篡改"需在 verify 命令执行原子窗口内改文件,实测极难;且 verify 命令本身可加 `flock` 串行化(实施细节,T-NNN 定)
- **手动 Edit evidence 的合法路径**:架构师明示豁免(如修正历史 evidence 笔误)——需 approved 决策覆盖 + 在 commit message 标注 `evidence-manual-edit: D-NNN`,pre-commit 见此标注 + covering decision 存在则放行

这个定论把"verify 写入 vs 手动 Edit"的区分从口号变成可机器校验的 provenance 字段。

| 时间漂移 | D-038a + D-038b 连续比对代码指纹 |
| 锚点漂移 | D-038a `code_fingerprint` 让"被验证代码"显式可见,可审计 verify 是否对准正确文件 |
| 声明漂移 | D-038c 视图化,事实状态不再由人工维护 |

| 决策漂移 | D-038d 信任分级,approved 不再被误读为"已落地" |
| **evidence 篡改**(评估新增) | D-038a `evidence_manifest_sha256` + protected_paths + D-038b 第一步完整性自证 |
| **WRITE-SET 二阶漂移**(评估新增) | D-038a `write_set_snapshot` + D-038b 第二步 WARN 级检测 |
| **跨平台 EOL 假 DRIFT**(评估新增) | D-038a 用 `git ls-files -s`(index blob sha,已 EOL 归一化)+ 前置 `git add` 检查(复审必改 #2 修正) |
| **T2 通胀**(评估新增) | D-038d 迁移期分档 + 批量补 code_fingerprint |

| **evidence 篡改三处一起改攻击**(复审新增) | D-038a `write_provenance` 字段 + D-038d #7 定论 pre-commit 校验 provenance.commit=HEAD |

剩余边界:verify 命令本身的语义正确性(验证的是不是真 AC)无法纯机器判定——归 v6.12.1 已有的 tautology WARN + 架构师批准任务卡时批准 verify 的人工环节,不试图机械化。**tag 漂移**(git tag 被删/force-move)未完全覆盖——D-038c 派生时校验 tag 指向的 commit 与 VERSION 文件声称的 commit 一致可缓解,但无法防 tag 被物理删除,归 git 仓库权限管理。

## Rationale

- **为什么不重跑 verify**:成本高(可能跑测试套件)、可能有副作用、不一定幂等;指纹比对 O(N) 廉价且无副作用
- **为什么 code_fingerprint 取 WRITE-SET 而非全仓**:聚焦被验证代码,避免无关改动误报 DRIFT;副作用:WRITE-SET 之外的依赖文件(helper)漂移无法检测(false negative),这是有意识的 trade-off
- **为什么用 `git ls-files -s` 而非 `git hash-object`/`sha256sum`/`Get-FileHash`**(复审必改 #2 修正):`git hash-object` 对未 staged 的工作树文件算原始字节(含 CRLF),与 `sha256sum` 无本质区别——评估 P0-2 的"已 EOL 归一化"论断是技术错误;`git ls-files -s` 取 index blob sha(归一化发生在 `git add`,由 `.gitattributes` 控制),跨平台一致。前置要求:WRITE-SET 文件必须 `git add` 进 index(verify 命令检查未 add 则 FAIL)
- **为什么 evidence 纳入 protected_paths**:evidence 是 drift-check 的信任根,不保护则一行 Edit 即绕过(评估 P0-1);generated-cache 定位不变,只是改它需 approved 决策覆盖
- **为什么 drift-check 撤出 pre-commit**:hook 已 L400+ 过载(L234 closing、L367 AC PASS、L375 dist-stale 等多分支),staging 语义模糊(staged vs working-tree hash 不一致),且 pre-commit 已有 dist-stale 第 8 分支,再加 drift-check 第 9 分支脆弱性陡增(评估 P1-4)
- **为什么状态面板视图化而非删除**:agent 需要快速状态概览,但概览必须可校验;派生视图兼得
- **为什么留 T2 信任级**:approved 决策、人工状态有真实价值,不能一刀切删除,但必须与 T1 区分;迁移期 T2 分档(`legacy-evidence` vs `declared-only`)保留区分度
- **为什么不并入 D-019e token 账本**(评估兼容性 #4 修正):**不严格正交**。漂移是正确性,账本是预算,但 T1/T2/T3 标签注入消耗同一份 SessionStart 预算。本决策声明标签计入 D-019e 预算,从别处省——而非声称"正交"忽略冲突

## Non-goals
