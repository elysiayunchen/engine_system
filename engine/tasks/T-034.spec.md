## 设计要点(实施时参考)

### checkpoint.md 模板
```markdown
# Checkpoint — T-NNN
> Last updated: <YYYY-MM-DD HH:MM> by <verify run>

## 已完成 AC
- [x] AC-1 <一句话摘要> — evidence/AC-1.json PASS
- [x] AC-2 <一句话摘要> — evidence/AC-2.json PASS

## 关键中间状态
- <已确认的接口 / 已写入的文件 / 已通过的子行为>

## 当前进行到
- AC-3 进行中:<当前步骤>

## 下一 AC 指针
- AC-4 <待执行摘要>
```

### 软门禁阈值(基于 P1 子代理审视)
| 阈值 | 触发 | 处置 |
|------|------|------|
| AC 数量 > 12 | WARN(原 8 上调,因 T-031 实证 8 AC 是合理发布单元) | 拆卡或声明 checkpoint_plan |
| WRITE-SET 独立路径 > 15(去重镜像对) | WARN | 拆卡或声明 checkpoint_plan |
| estimated_steps > 20 | WARN | 拆卡或声明 checkpoint_plan |
| 缺 estimated_steps 字段 | WARN(仅对新卡,存量卡不告警) | 补字段 |
| depends-on 上游未 done | FAIL | 阻塞下游置 active |

### 软门禁处置
- 任一 WARN 触发:架构师须二选一
  - **拆卡**:把超阈任务拆成多张子卡,显式 depends-on
  - **声明 checkpoint_plan**:在任务卡加 `checkpoint_plan: 每 N 步强制 checkpoint`,N 由架构师定
- 不拆不声明 = FAIL,不允许置 active

### depends-on 字段
- 任务卡头加 `depends-on: T-NNN, T-NNN`(逗号分隔)
- Doctor 检查:depends-on 列表中任一卡 status != done → 本卡不允许置 active(FAIL)

### SessionStart 重锚优先级
1. checkpoint.md(若存在)— AC 级完成状态
2. progress.md(若存在)— 任务级进行中状态(覆盖 §4)
   - **注**:本档位为 T-032 落地后激活的兼容层,T-032 未落地时退化为 #1 checkpoint.md → #3 任务卡头直连(与 D-028 §7 依赖关系审视一致)
3. 任务卡头(GOAL/WRITE-SET/FORBIDDEN)
4. HANDOFF 立即恢复点(薄指针,指向 progress.md §4)
   - **注**:本档位为 T-032 落地后激活的兼容层,T-032 未落地时不存在(HANDOFF 仍按原有会话级职能存在,但不再作为薄指针指向 progress.md §4)

### checkpoint.md 生命周期
- **active / paused**:留在 `engine/evidence/T-NNN/checkpoint.md`(verify 脚本持续追加写)
- **done**:归档到 `engine/archive/tasks/T-NNN-checkpoint.md`(与 progress.md / HANDOFF 归档同款策略,不进 SessionStart 注入)

### 与 progress.md 的写入职责分离
- verify 脚本只写 `checkpoint.md`(AC 级完成状态追加)
- agent 只写 `progress.md`(任务级进行中状态更新)
- 两者写入路径分离,无并发写冲突(verify 在 AC PASS 后写入,agent 在步骤推进时写入,时机与文件均不同)

### 显式不做
- 不硬失败大任务(软门禁,可选拆卡或 checkpoint_plan)
- 不替代 progress.md(checkpoint 是 AC 级完成状态,progress 是任务级进行中状态)
- 不引入动态上下文预算感知(超出本任务范围)
- 不强制 workstream 改造(workstream 是同卡并行,跨卡串行靠 depends-on)
